## Operational link hypotheses (do not implement automatic joins yet)

1. **PLATEAU ↔ GSI:** choose one municipality and an explicit common acquisition-era window; compare only published coverage footprints and legal permitted reuse. A later bounded study may project GSI building exterior lines and PLATEAU CityGML LOD0/LOD1 footprints into a documented common metre-based CRS, repair only explainable geometry defects, and compute aggregate intersection/union, split/merge, and date-mismatch rates. Retain native dataset/building identifiers and lineage separately; geometry overlap is not proof of legal building identity.
2. **PLATEAU ↔ J-SHIS:** intersect only a reviewed mesh polygon with reviewed building geometries, preserving J-SHIS version, hazard intensity measure, exceedance probability and exposure-time horizon. Site amplification factors are not fragility curves, damage rates or event observations. No asset-level deterministic damage, insured sum, replacement cost or insurer attribution from overlay.
3. **PLATEAU / GSI ↔ OSM / Microsoft / Overture / GlobalBuildingAtlas:** any comparative exercise must first identify common upstream footprint imports, licence incompatibilities and release vintages. Do **not** count aligned polygons as independent validation without source-lineage checks. GlobalBuildingAtlas LoD1 height sources are not interchangeable with the separately licensed ODbL polygon subset.

## Proposed smallest rights-safe technical experiment

- **T0 — exact provider metadata:** identify one municipality PLATEAU catalogue record (city, fiscal release, dataset ID, stable provider landing URL, CityGML LoD, rights) and one GSI mesh in the same area; identify one J-SHIS versioned mesh/map edition. Record authoritative terms timestamp, attribution and allowed action separately for all three.
- **T1 — strictly bounded access:** permit at most one fixed *anonymous, metadata-only* PLATEAU catalogue/API probe after verifying the endpoint-specific API terms and redirect policy. Use a small response cap, fixed URL and timeouts, no pagination or downloads. **No** GSI credentialed request without authorization/rights review; J-SHIS first uses provider metadata and version documentation only.
- **T2 — original asset proof (new PR):** only after exact licence, intended commercial/derived/raw use, privacy and attribution decisions, fetch one predeclared small original provider file to transient isolation; verify response length, SHA-256, native file format, object count, CRS/axis/vertical datum, measured-height units, LoD, null coverage, dates and any duplicate IDs; do not persist raw bytes in Git.
- **T3 — scientific evidence:** bounded aggregate overlap/confusion matrix with one city and one comparison mesh, source lineage and independent holdout. No import to an exposure database or use in catastrophe loss calculation until additional review and admission.

## Fail-closed acceptance criteria

- No join that treats a PLATEAU feature, GSI exterior line and insurance risk as the same entity solely because geometries overlap.
- No building-height inference from J-SHIS site amplification or from PLATEAU LOD1 coordinates where the source does not provide an admissible measured-height field and verified vertical datum.
- No treating probabilistic hazard (for example a 50-year exceedance statistic) as an individual quake footprint or damage observation.
- No claiming 100% Japan-wide building coverage or construction year completeness; list municipal releases and per-field missingness first.
- No anonymous-GSI access bypass, no bulk data acquisition and no commercial/redistribution permission extrapolation from general programme pages.

## Implemented offline PLATEAU catalogue gate (synthetic tests only)

The fixed Shinjuku municipality code `13104` and fiscal CityGML release year `2024` are illustrative identifiers from the official PLATEAU REST API documentation; they do **not** prove the currently live API returns that release. `python research_runners/plateau_citygml_catalogue_preflight_v0.py --input /path/to/externally-held-catalogue.json` validates only a previously lawfully supplied offline JSON catalogue. It requires exactly one concrete target release, consistent city and prefecture IDs, usable feature-type metadata including `bldg`, valid fiscal years, spec, safe URL field syntax and source metadata caps; it explicitly refuses a `latest` release as a historical identity. When the provider supplies `composite_url`, it must be the documented exact `https://api.plateauview.mlit.go.jp/datacatalog/citygml/13104-2024/citygml.zip` fixed-year redirect; a missing one is reported as `fixed_year_composite_url_present=false`, not silently replaced by a mutable alias. Raw `url` metadata is screened for HTTPS, public host shape, credentials, queries, fragments and unsafe path syntax but is never fetched. No stable release is assumed from URL shape alone because redirect destinations and CMS original bytes remain unverified. The diagnostic emits only bounded structural booleans, target city/year, a hash of user-supplied input, and provenance/approval=false flags. There is no network client, building-geometry parsing, original ZIP download, live receipt or CAT admission. See synthetic adversarial regression tests in `tests/test_plateau_citygml_catalogue_preflight_v0.py`. Official PLATEAU documentation says the unfiltered REST catalogue can exceed 2 MB. This **offline-only input budget is now 8 MiB**, independently of the still-disallowed **64 KiB hypothetical network probe** in the source-access contract. Files larger than 8 MiB fail closed, and accepting a previously supplied local file grants no HTTP/network access. The catalogue's optional `citygml[].file_size` value is CMS original ZIP size metadata when available; optional `gspatialjp_files[].file_size` values belong to individually linked G-Spatial archives and may correspond to a different vintage. The REST preflight checks both sizes independently as positive signed int64, records whether metadata for each are known and exposes only structural flags/counts. Neither field proves any original ZIP bytes have been acquired or verified, and no source URLs or raw size values are emitted.

## Alternative: small, fixed Shinjuku CityGML GraphQL metadata response

Official GraphQL docs describe `citygmlDatasets(input: CityGMLDatasetsInput)` with `cityCodes` and `years` filters; the `CityGMLDataset` type exposes `cityCode`, `prefectureCode`, `year`, `registrationYear`, `url`, `compositeUrl`, `featureTypes` and `metadataZipUrls`. The static GraphQL schema reference display currently omits `fileSize`, **but** the provider's CityGML guide explicitly describes optional GraphQL `fileSize` for CMS ZIP bytes. Because those two official documents disagree, the narrow fixed GraphQL query now deliberately omits `fileSize` until a verified live schema/terms review. This is a **minimal selected field set**, not a claim that the provider cannot expose that field. See https://docs.plateauview.mlit.go.jp/api/graphql/schema/ and https://docs.plateauview.mlit.go.jp/api/graphql/ .

The new strictly non-executable access contract `access/jp.mlit.plateau.graphql.citygml-shinjuku2024.json` documents **one exact possible future** read-only POST to the official `/datacatalog/graphql` endpoint. Its static query is pinned to city `13104`, fiscal year `2024`, and the minimal field set. **Nothing in this PR authorizes making that network request**. Only endpoint- and dataset-specific rights review can authorize a real bounded call, with request-body exactness, response cap, redirect/DNS review and date-stamped byte receipt.

The same offline preflight runner now supports `python research_runners/plateau_citygml_catalogue_preflight_v0.py --format graphql --input /path/to/lawfully-supplied-response.json`. This GraphQL mode accepts at most 64 KiB of local metadata and requires exactly one matching city/year, one distinct native GraphQL ID, `bldg` among unique feature types, and an actual HTTPS CMS URL. It validates the exact documented nine-field GraphQL selection, checks that `prefectureCode` matches `13`, counts HTTPS `metadataZipUrls` without exposing them, and explicitly sets `cms_original_size_metadata_known=false` because this **particular GraphQL query deliberately does not select** the disputed optional size field. It rejects GraphQL errors, multiple records, extra response fields not requested by this exact query (including `fileSize`), unpinned latest redirects and malformed URLs. The provider's CityGML guide independently documents optional **REST row-level** `file_size` for the CMS ZIP; the REST offline preflight validates it as separate from `gspatialjp_files[].file_size` for other G-Spatial archives. Neither metadata size constitutes a verified original byte receipt. See https://docs.plateauview.mlit.go.jp/datasets/citygml/ for the explicitly described REST row-level and optional GraphQL `fileSize` semantics. The returned diagnostic contains no original provider URLs/ID, no individual building attributes, and no model/source approval. In particular, synthetically passing this code does **not** prove the GraphQL server will return that response or grant data reuse rights.

## Local acquisition-receipt input safety

The offline CLI's `--input` now reads through a bounded, single-open regular-file descriptor rather than trusting a separate `stat` and `Path.read_bytes`. The local file must be a nonempty regular file within the specific REST 8 MiB or GraphQL 64 KiB budget; final-component symlinks, FIFOs, device files, directories, unreadable files and changing `size`/`mtime`/`ctime` during the read fail closed. Error responses do not print the local input path or source bytes. The corresponding tests use **only synthetic bytes**, including an actual temporary symlink and FIFO on POSIX. This is about secure reading of an independently and lawfully supplied local receipt candidate: **it does not authorize provider downloads or validate that an input actually originated from MLIT**. File hashes remain observed-input evidence rather than provider-authenticated artefact identity.

## Existing OpenCatastrophe boundaries

Retain landscape discovery as `not_admitted`. This PR adds two independent non-executable PLATEAU access contracts: a T0 full REST catalog in `access/jp.mlit.plateau.citygml.3d-city-models.json` for the officially documented `GET /datacatalog/plateau-datasets`, and the filtered T0 GraphQL documentation-only path in `access/jp.mlit.plateau.graphql.citygml-shinjuku2024.json`. It deliberately remains `documented_only` with `probe_contract.mode=none`: unknown service automation terms, a potentially oversized unfiltered response, and mutable 'latest' releases block an actual probe. J-SHIS now has a static contract `access/jp.nied.jshis.pshm.site-amplification.json` with `restricted_by_terms`, `do_not_automate` and `probe_contract.mode=none`. GSI also has an explicit static contract `access/jp.gsi.fgd.building-outline.gml.json` with `blocked_registration`, `do_not_automate` and `probe_contract.mode=none`; provider-account registration and Survey Act rights are not bypassed. The J-SHIS terms are binding for the public-source pathway, not an approval to publish a raster, derived commercial products or CAT inputs. No manifest or model run-evidence is created. Technical probes require a new bounded source-specific review, while admitted uses require accepted `manifests/` plus source review. Existing European building overlap lessons (notably Luxembourg/EUBUCCO) are a methodological precedent, not evidence that the Japan identity matching problem has already been solved.
